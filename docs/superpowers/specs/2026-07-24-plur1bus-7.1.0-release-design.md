# PLUR1BUS 7.1.0 Release Design

**Date:** 2026-07-24
**Status:** Approved for implementation planning
**Release title:** `PLUR1BUS 7.1.0 - Not just an agent. Yours.`

## Objective

Publish the audited PLUR1BUS state currently on `origin/main` as version
`7.1.0` through three independently verified distribution channels:

1. a GitHub Release with an installable package asset;
2. GitHub Packages as `@cyb3rb1ade/plur1bus-memory@7.1.0`; and
3. ClawHub as PLUR1BUS version `7.1.0`.

The release must also update the current user-facing documentation and prove
that a fresh OpenClaw installation works. The release contains no new runtime
feature work.

## Current Baseline

The release branch starts from merged `origin/main` commit
`f1ec54c68b67dbf5d95e5ce13c232fce4c7294ee`.

The clean baseline was verified before release planning:

- `npm ci --ignore-scripts`: passed, 0 vulnerabilities;
- full serial test run: 3,260 tests, 3,259 passed, 0 failed, 1 skipped.

The current package, lockfile root, and OpenClaw plugin manifest are versioned
`7.0.0`. The nested private emotional-state-injector extension is independently
versioned `1.0.0`.

## Chosen Release Strategy

Use a short-lived `release/7.1.0` branch and a PR into `main`.

1. Prepare and verify the version and documentation changes on the release
   branch.
2. Push the branch and open a release PR.
3. Require the repository checks to pass, then merge the PR.
4. Create `v7.1.0` from the resulting `main` commit.
5. Publish and verify each distribution channel from that immutable source.

This adds one CI gate before immutable publication while preserving a concise
release path. Direct commits to `main` and a separate release candidate were
considered and rejected.

## Version and Metadata Changes

Set the following files to `7.1.0`:

- `package.json`;
- the root package entries in `package-lock.json`; and
- `openclaw.plugin.json`.

Keep these identities stable:

- npm package: `@cyb3rb1ade/plur1bus-memory`;
- OpenClaw plugin ID: `memory-lancedb-namespaced`;
- OpenClaw plugin display name;
- nested emotional-state-injector version: `1.0.0`; and
- minimum Node.js version: `>=22.5.0`.

The requested phrase is a release title and README claim only. It must not
replace the persistent plugin display name.

## Documentation Scope

Update every current user-facing release and installation document:

- root `README.md`;
- `CHANGELOG.md`;
- `docs/release-checklist.md`; and
- any current installation instructions that mention a version, tag, package
  source, or minimum runtime.

The README must show version `7.1.0`, use the approved release claim, summarize
the important changes since `v7.0.0`, and document the supported installation
sources without implying that GitHub Packages is anonymous when authentication
is required.

The changelog and release notes must be derived from the complete Git history
from `v7.0.0` through the release commit. They must cover the completed audit
remediation, dependency and Node.js floor changes, operational impact, upgrade
notes, verification, and known limitations. The pre-existing reranker scoring
quality bug remains a separately tracked known issue.

Historical audit-evidence README files are immutable evidence, not current
release documentation, and must not be rewritten.

## Package Construction

Create one canonical npm tarball from the verified release source with
`npm pack`. Inspect the dry-run and final file lists before publication.

The package gate must verify:

- expected runtime and documentation files are present;
- test fixtures, secrets, credentials, local state, and unrelated audit
  evidence are not accidentally included;
- package name, version, Node engine, plugin manifest version, and repository
  metadata agree;
- package size is recorded; and
- a SHA-256 checksum is generated.

The GitHub Release receives the canonical `.tgz` and checksum as assets.
GitHub Packages receives the same source state through an explicit
`https://npm.pkg.github.com` publish command. The repository must not silently
redirect ordinary npm publication unless a documented `publishConfig` change
is deliberately required.

## Installer Verification

Installer behavior is a mandatory release gate, not documentation-only work.
All smoke tests use disposable temporary OpenClaw homes and must not alter the
operator's live installation.

Before publication:

1. install the canonical local tarball through the supported OpenClaw local
   package installation path;
2. verify plugin discovery, manifest loading, version reporting, and a minimal
   startup/doctor path;
3. verify the existing installer/updater regression suite; and
4. uninstall or discard the temporary home by removing only its explicitly
   created temporary directory.

After publication:

1. download and checksum-verify the GitHub Release asset, then repeat the fresh
   install smoke;
2. install `@cyb3rb1ade/plur1bus-memory@7.1.0` from GitHub Packages in an
   isolated authenticated environment and verify the installed package and
   plugin manifest;
3. install the exact ClawHub `7.1.0` version into another temporary OpenClaw
   home and repeat plugin discovery and startup/doctor checks.

A registry download alone is insufficient: the verification must reach the
OpenClaw plugin-loading boundary wherever the supported installer permits it.
If a channel cannot be installed by OpenClaw directly, the package must first
be materialized from that channel and then passed to the supported local
installer, with that two-step path documented.

## Verification Gates

Before the release PR is merged:

- `npm ci --ignore-scripts`;
- `npm audit`;
- `npm run lint`;
- `node --test --test-concurrency=1 tests/*.test.js test/*.test.js`;
- `git diff --check`;
- version synchronization checks;
- package dry-run and package-content inspection; and
- local tarball installer smoke.

After the PR is merged, repeat the source-state and packaging checks on the
exact prospective tag commit before creating the tag. GitHub CI for the release
PR must be green.

After each publication, query the destination to verify exact version, source,
assets, checksums, and installability. The final report must distinguish the
three publication results.

## Publication Preflight and Order

Before editing or publishing, confirm:

- tag `v7.1.0` does not already exist locally or remotely;
- GitHub Release `v7.1.0` does not already exist;
- GitHub Packages version `7.1.0` is not published;
- ClawHub version `7.1.0` is not published;
- GitHub, GitHub Packages, and ClawHub authentication is available; and
- the GitHub token has package-write and release permissions.

Publication order:

1. merge the green release PR;
2. update and verify local `main`;
3. create and push annotated tag `v7.1.0`;
4. publish GitHub Packages and verify its package metadata/install path;
5. create the GitHub Release with the exact approved title, release notes,
   canonical tarball, and checksum;
6. verify the GitHub asset installation;
7. run the ClawHub dry-run from the immutable GitHub tag;
8. publish ClawHub `7.1.0`;
9. inspect ClawHub source linkage and run its fresh-install smoke.

The release is complete only when all three channels and installer checks are
reported successfully.

## Failure and Recovery Policy

Published versions and pushed tags are treated as immutable.

- Before the tag is pushed, failures may be corrected on the release branch and
  reverified.
- After the tag is pushed, do not move or overwrite it.
- After any registry accepts `7.1.0`, do not overwrite or reuse that version.
- On a partial publication failure, stop, preserve successful artifacts, report
  the exact boundary, and resume only the unpublished channel after correcting
  the cause.
- Never expose tokens, registry credentials, temporary npm configuration, or
  installer-local secrets in logs, commits, release notes, or reports.

Rollback guidance for users points to the immutable `v7.0.0` GitHub and ClawHub
versions. Existing memory data is not deleted or migrated by the release
process.

## Out of Scope

- new PLUR1BUS features or behavioral refactors;
- changing the plugin ID or permanent display name;
- changing the nested emotional-state-injector version;
- publishing to the public npmjs registry;
- rewriting historical audit evidence; and
- fixing the separately existing reranker scoring quality issue.
