# PLUR1BUS Hermes 0.3.0 Release Design

## Goal

Build and publish a dedicated Hermes installer release based on the existing
PLUR1BUS `v7.2.6` release. The OpenClaw `main` branch, `v7.2.6` tag, and 7.2.6
GitHub release remain unchanged.

## Integration Strategy

Merge the annotated `v7.2.6` tag into `codex/plur1bus2hermes`, preserving the
same non-rewriting branch history used for the 7.2.3 Hermes release. Resolve
conflicts by keeping the released 7.2.6 OpenClaw implementation authoritative
while retaining the Hermes provider adapter, controls plugin, installer,
platform-aware Jina retrieval sidecar, and OpenClaw compatibility.

## Version Contract

- OpenClaw/npm package: `7.2.6-hermes.1`
- Hermes Python provider and controls packages: `0.3.0`
- Hermes plugin manifests: `0.3.0`
- Git tag: `hermes-v0.3.0`
- GitHub release title: `PLUR1BUS Hermes 0.3.0 — 7.2.6 installer release`

Version references in package manifests, lockfiles, installer output,
documentation, and release metadata must agree.

## Installer Behavior

The 0.3.0 installer preserves the behavior shipped by `hermes-v0.2.0`:

- Detect Hermes installations automatically and prompt when several instances
  are available.
- Require an explicit Hermes home for noninteractive installation before any
  writes.
- Keep the selected Hermes chat provider, endpoint, and model authoritative.
- Use independent embedding and reranking routes for Auto-Recall.
- Offer the optional platform-aware Jina sidecar: MLX on supported Apple
  Silicon and portable Transformers elsewhere.
- Require explicit acceptance of the Jina models' CC-BY-NC-4.0 license, use
  pinned revisions, and activate retrieval only after a real smoke test.
- Preserve populated LanceDB stores and their existing vector space.
- Keep the package installable and operational under OpenClaw.

No fresh-install default may inject a user-specific model, endpoint,
credential, transport, profile, or trust setting.

## Validation

Before release:

1. Confirm the merge contains the exact `v7.2.6` commit.
2. Run `git diff --check` and version-consistency checks.
3. Run the complete Node test suite and all Hermes installer/provider tests.
4. Run package audit and lint checks required by the repository release gates.
5. Inspect `npm pack --dry-run`, build the real tarball, and verify that the
   Hermes installer/provider files and all 7.2.6 deploy-manifest scripts are
   included.
6. Calculate and independently verify the tarball SHA-256 checksum.
7. Exercise installer dry-run/noninteractive safety paths without modifying an
   existing user memory store.

Any failed gate blocks publication until its cause is resolved and the relevant
gate is rerun.

## Publication

Create a release commit on `codex/plur1bus2hermes`, then create and push the
annotated tag `hermes-v0.3.0`. Push the Hermes branch without changing `main`.

Publish a GitHub prerelease matching `hermes-v0.2.0`, including:

- installation instructions using `--branch hermes-v0.3.0`;
- Python installation examples pinned to `hermes-v0.3.0`;
- highlights and compatibility notes;
- `cyb3rb1ade-plur1bus-memory-7.2.6-hermes.1.tgz`;
- the matching `.sha256` file.

Publish `@cyb3rb1ade/plur1bus-memory@7.2.6-hermes.1` to GitHub Packages with the
`hermes` dist-tag. The `latest` dist-tag remains unchanged. Registry publication
is considered complete only after querying the registry and confirming both the
exact version and the `hermes` dist-tag.

## Recovery and Safety

Do not rewrite or force-push branch history. Do not move or replace `v7.2.6`.
If publication partially succeeds, report each surface independently: branch,
tag, GitHub release, assets, package version, and dist-tag. Existing local
Hermes installations and memory databases are outside the release-build write
scope.
