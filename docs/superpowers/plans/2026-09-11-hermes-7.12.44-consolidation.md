# Hermes 7.12.44 Semantic Merge and Consolidation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Make semantic merge and daily consolidation proposals genuinely
actionable in Hermes while preserving its reviewed durable replacement protocol.

**Architecture:** Extend `durable_merge.py` and the existing revision-bound
operator apply path. LLM output is untrusted proposal content, never authority.
Keep native lossless/default-off automatic behavior; add explicit semantic
proposal configuration instead of silently relaxing historical safety defaults.

**Tech Stack:** Python, LanceDB, internal LLM interface, scoped jobs and controls.

**Spec:** `docs/superpowers/specs/2026-09-11-hermes-7.12.44-design.md`

## Task 1: Review-first semantic store merge proposals

**Files:** `automatic_merge.py`, `durable_merge.py`, scoped runtime merge entry
points, controls merge listing if needed; tests `test_semantic_merge.py` and
existing durable/automatic merge suites; tracked audit.

- [ ] Read current `try_store_merge`, `build_proposal`, `preserves_facts` and
  `apply_merge_proposal` contracts. Keep their lossless default behavior and
  existing durable retry semantics intact. Add a documented explicit semantic
  proposal mode; default is off, and semantic mode does not imply auto-apply.
- [ ] RED: two compatible same-scope claims produce one inspectable semantic
  proposal with source snapshots, proposed text and stable source-bound identity,
  while both sources remain available before approval. Existing controls must
  list it and bind approval to its exact immutable revision.
- [ ] Request bounded structured proposed text from the internal LLM. Require
  the existing conservative fact-token/number guard plus contradiction and
  disjoint-validity refusal. Treat this guard as a conservative rejection filter,
  not proof that an LLM never invents facts. Operator review remains mandatory.
  No output-controlled file path, ID, scope, origin or approval fields.
- [ ] Materialize the incoming claim independently while a review-only proposal
  is pending. Bind both actual persisted source IDs/snapshots in the proposal;
  do not treat an incoming-only snapshot as a second persisted row accidentally.
  Failed/uncertain proposal generation falls back to ordinary separate storage.
  Once application begins, use the durable apply/repair protocol, never a second
  plain insertion on an uncertain destructive outcome.
- [ ] Re-embed proposed text using the current encoder before application;
  verify finite vector, dimension AND fingerprint. Revalidate both sources,
  validity, lineage and scope before retiring either. Extend the durable proposal
  schema explicitly if it cannot represent two persisted sources; retain legacy
  one-source store proposals and repair compatibility with regression tests.
- [ ] Test fact loss, contradiction, foreign scope, expired/invalidated/core
  source, disjoint bounds, malformed model JSON, bad vector, encoder change,
  source drift, stale approval, retry and replacement-write failure. All refusals
  retain originals. No approval is manufactured by a model call.
- [ ] Run semantic, automatic, durable merge, validity and controls regressions;
  record exact commands/results and intentional default differences; commit and
  independent security/state-machine review.
