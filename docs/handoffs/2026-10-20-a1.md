## Controller contract

- `memory.stats(ids: readonly string[] | undefined, p, a)` → `{agentId,items:[{id,recalls,distinctQueries,lastRecalledAt}]}`. Max 500 UUIDs, per requesting agent and ACL-visible/live cards; explicit unseen counters zero, omitted IDs enumerate persisted counters. Last recall time is epoch ms or null.
- `memory.promote({ids},p,a)` → `{agentId,items:[{id,outcome:'promoted'|'skipped',reason}]}`. Foreground system/user only; an authorized Harness scheduler uses explicit `{origin:"system",background:false}` as for import, independently of its outer cron trigger. Model calls must never receive that context. Reasons: integrated/disabled/lock-busy/not-found/not-live/scope-not-publishable/already-promoted/cap-reached. Only integrated is promoted; receipt follows atomic Markdown write. Config cap `schicht15.maxPromotionsPerRun` per call, 0 unlimited, no call-level override.
- Job `knowledge-update`: pending queue per agent, same primitive, singleton, no LLM and no dreaming LLM breaker consumption.
- `memory.curation.list({limit?},p,a)` → `{agentId,items:[{id,status,text,category}],truncated}`; `resolve(id,'keep'|'drop',p,a)` → `{id,ok,status?,reason?}`. Foreground human only; ACL and mandatory audit. Separate from D31 memory.proposals.
- Capabilities: recallStats/knowledgePromotion/memoryCuration all true, alongside memoryLink.

Recall counters are a private SQLite sidecar per agent. HMAC query digests only,
no plaintext query or memory text. Schema 0 → 1 migration is idempotent; existing
LanceDB rows are untouched and historical pre-contract recall counts unknown.
Only complete record elements surviving the Engine's render cap count; stricter
host delivery limits remain the host's responsibility. Warm/degraded calls do not
count. A statistics write error warns without failing recall; explicit reads fail.

Knowledge writes preserve existing content verbatim and append quoted source
facts deterministically. Source markers guarantee replay idempotency even across
write/queue-cleanup crashes. The public primitive rejects model/background calls;
shared copies need a later explicit publication policy. Semantic rewriting and
retiring obsolete curated statements remain later curation/tree work.

### Recall-statistics synchronous-write measurement

Reproduce from the Engine checkout, with its exact dependencies installed:

```sh
export PATH=/Users/cyberblade/.node24/bin:$PATH
node scripts/bench-recall-stats.mjs
# Optional scratch parent on a filesystem of interest:
node scripts/bench-recall-stats.mjs /tmp
```

Measured 2026-10-21 on Apple M5 Pro, arm64 macOS (Darwin 27.2.0), Node 24.21.0,
local macOS temporary storage. Three consecutive runs under normal shared
development-host activity; each call records **20 UUIDs**. Nearest-rank p95
uses 100 new-sidecar samples or 500 steady samples after 50 warmups.

| Scenario | p95 run 1 ms | p95 run 2 ms | p95 run 3 ms | Largest observed ms |
| --- | ---: | ---: | ---: | ---: |
| New sidecar/schema, first write | 0.900 | 6.013 | 5.826 | 11.448 |
| Existing sidecar, repeated query | 0.591 | 0.550 | 0.517 | 31.531 |
| Existing sidecar, distinct query per call | 1.879 | 17.075 | 2.181 | 57.493 |

The timed region includes the actual synchronous `record()` path: path checks,
directory creation, SQLite open, chmod, pragmas/schema checks, `BEGIN IMMEDIATE`,
20 counter/query writes, commit and close. Every call opens its own handle even
after warmup; committed counters and distinct counts are verified outside the
timed region. Distinct-query runs grow to 11,000 query rows (550 × 20).
Factory/module import and cleanup are outside the timer. New sidecar means
schema-cold, **not** cold OS/page/disk caches. No cache flushing, extra fsync
beyond SQLite defaults, competing writers, slow/network storage or disk-pressure
stress is applied. This measures the sidecar operation, not end-to-end recall,
LanceDB retrieval, model/embedding time, or event-loop delay distribution.
The variation and outliers are retained above; this is no universal latency
guarantee. In contention `BEGIN IMMEDIATE` may block up to the configured
5,000 ms busy timeout. The synchronous implementation remains unchanged; any
buffering/connection-lifecycle redesign needs separate latency/durability scope.
